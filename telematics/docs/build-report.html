01

What this system actually is

Plain English

A GPS box bolted to a machine (excavator, generator, truck) phones home over the mobile network every few seconds. This system answers that phone call, writes down exactly what it said, works out whose machine it is and how many hours the engine has run, and hands that to a dashboard — and eventually to an invoice and a WhatsApp alert. The whole point is that the number that ends up on an invoice can survive a dispute: it has to be traceable back to the exact bytes the machine sent, untouched.

Technical

A Node.js TCP/HTTP harness implementing the real Teltonika Codec 8/8E wire protocol end to end: ingestion → decode/normalise → enrichment → a tenant-isolated Postgres/memory store → a read API, a utilisation ledger with tamper-evident sealing, a rules engine, and WhatsApp delivery. Split into 9 independently-testable modules plus an operability layer (logging, lifecycle, tooling), built against 9 explicit correctness invariants that are enforced by tests, not convention.

The full module-by-module data flow is drawn out in the companion flowchart artifact. This report goes one layer deeper: what each piece is worth, how the team keeps itself honest, and what still needs a human before any of it touches a real customer.

02

The 9 modules — what each does, and how good it is

Every module below was graded against three things: does it work (tests), was it independently checked (the two audits below), and is it safe to rely on today. "Solid" means built, tested, and reviewed. "Blocked" means the code is fine but something outside code — hardware, a human sign-off, a vendor credential — has to happen first.

M0Protocolsrc/protocol/solid

Plain English

The translator that turns the raw bytes a GPS box sends into numbers the rest of the system understands — like knowing the exact dialect the device speaks.

Technical

Pure functions over Buffers: CRC-16/IBM, IMEI framing, AVL record encode/decode for Codec 8 & 8E. Verified byte-for-byte against Teltonika's own published canonical test packet.

Why trust it: no I/O, no state — it either matches the spec or the test fails. Zero open findings.
M1Ingestionsrc/ingestion/solid, hardened

Plain English

The phone line the GPS box calls into. It only says "got it" after your data is actually saved, so nothing is lost if the call drops mid-sentence.

Technical

ACK-only-after-durable-write, idempotent resend, per-IP handshake rate limiting, packet-size cap, socket idle/handshake timeouts, codec allowlist, IMEI format validation.

Known gap: no TLS and no per-device secret on the port yet — anyone who can reach it and guess a valid 15-digit IMEI can attempt a handshake. Flagged, not yet closed.
M2Decode / normalisesrc/decode/solid

Plain English

Turns a raw reading into a clean fact — and, crucially, says "unknown" instead of guessing when a sensor genuinely didn't report anything.

Technical

Absent IO → null, never 0; engine hours only for CAN-mapped assets, always tagged source:'ecu'; per-record timestamp attribution; explicitly guards the minutes→seconds unit conversion (a silent 60× billing error no other test would catch).

Zero open findings.
M3Store & tenancysrc/store/, db/solid

Plain English

A locked filing cabinet — each customer can only ever open their own drawer, and nothing already filed can be quietly edited later.

Technical

Two adapters (memory / Postgres) behind one interface. Tenancy = row-level security; evidence immutability = a Postgres trigger. Both proven with negative tests — the policies/trigger were physically dropped and the tests confirmed they then fail.

The rare kind of "tested": someone deliberately broke the enforcement and watched the tests catch it.
M4Enrichmentsrc/enrichment/deliberately minimal

Plain English

A first rough guess at what the machine is doing right now — off, idling, moving. Enough to start with; not yet smart about full trips or work zones.

Technical

Derives coarse state (off/idle/moving/unknown) from ignition, movement, speed. Trip segmentation and geofence membership are not built here yet — the current geofence rule (M8) does its own standalone distance check instead.

Fine for a pilot; will need real growth before the product's trip/utilisation views feel complete.
M5Utilisation ledger & evidencesrc/ledger/built, not yet billable

Plain English

The accountant. It correctly totals engine hours from readings it trusts and seals the calculation so it can't quietly be changed afterward — but nobody has checked its math against a real machine yet, and a human still has to sign off before it touches a real invoice.

Technical

computeUtilisation() sums positive ECU-meter deltas per asset/period; meter resets and non-ECU readings are excluded, never blended in; sealUtilisationRecord() produces a deterministic, tamper-sensitive SHA-256 evidence hash. 11/11 tests, correct against spec and the seed scenario.

Blocked on: (1) reading AVL 102 off a real installed adapter and reconciling it against the machine's own physical hour-meter, (2) a human reviewing the billing math against real fleet data. Neither is a code problem.
M6Read API (surfaces)src/api/solid

Plain English

The window a dashboard looks through — every request has to say which customer it's asking for, or it's refused outright.

Technical

Zero-framework HTTP API (/health, /devices, /positions, /assets/:id/engine-hours). Every data endpoint requires X-Tenant-Id and is tenant-scoped by the store.

Zero open findings.
M7Messaging (WhatsApp)src/messaging/plumbing solid, send switched off

Plain English

The mailroom is built and knows exactly which letter goes to which customer without ever double-sending — it just isn't allowed to actually mail anything yet, because WhatsApp hasn't approved the message templates.

Technical

dispatch.js: template mapping, event-id dedupe, tenant isolation, partial-failure isolation — 9/9 tests. notify() itself is a throwing stub by design until live Meta credentials + approved templates exist.

Known gap: the delivered-message log is in-memory only — a process restart would currently re-send already-delivered messages once a real sender is plugged in. Needs durable storage first.
M8Rules & event detectionsrc/rules/broken → caught → fixed

Plain English

The system's instinct — "that machine just left the yard," "someone's running it after hours," "the harness got unplugged." The first version of this literally didn't run at all; an independent review caught it before anyone shipped it, and it was rewritten and proven working.

Technical

First delivery: a bad import crashed the module on load, and its "proof" test never executed a single assertion. Review found it, fix rewired the import, corrected a timezone bug (getHours() → getUTCHours()), fixed a minutes/ms threshold bug (60,000ms labelled "60 min"), and fixed an event-id collision. Now 12/12 tests, wired into messaging's dedupe.

See the review case study in §4 — this is the clearest evidence the QA process actually works.
M9Simulator / device benchsrc/simulator/solid

Plain English

A stunt double for the real GPS hardware that speaks the exact same language, so the whole system can be built and proven correct before a single physical device exists.

Technical

Deterministic (seeded PRNG, no Date.now/Math.random). 7 named scenarios, each exercising specific invariants. Doubles as the test bench for ingestion, replay, and tenancy tests.

Because it speaks the real wire protocol, a physical FMC130 drops in later with zero server-side changes.
P0Operability layersrc/logging/, src/lifecycle/, src/tools/solid

Plain English

The seatbelts: shutdowns that never lose data mid-save, logs that never leak secrets or customer data, and a stress test proving it survives 1,000 devices connecting at once.

Technical

Structured, secret-redacting JSON logger; SIGINT/SIGTERM drain with a hard deadline, verified on real OS processes (14/14 checks); a load-testing harness — 1,000 connections in one burst passed with zero errors (connect p95 ≈1.1s, ACK p95 ≈7ms, peak RSS ≈85MB).

Not a product module — this is why the slice is safe to run unattended.
03

How it all connects, and how it actually gets built

The data path, in plain terms

A device or the simulator dials in → Ingestion answers and only hangs up once it's saved the data → Decode turns bytes into facts → Enrichment makes a rough guess at machine state → it all lands in the Store, split cleanly by customer → from there, three things happen in parallel: the Read API feeds dashboards live, the Ledger quietly totals up billable hours and seals the evidence, and Rules watches for things worth alerting on and hands them to Messaging to WhatsApp someone. See the flowchart artifact for the full picture with every arrow labelled.

The build workflow, in plain terms

The project is split into gated phases (P-now → P0 → P1 → P2 → P3 → P4 in BUILD_PLAN.md/TASKS.md) — each phase has a hard gate (a specific test count green, a demo that produces exact expected numbers) that must pass before the next phase starts. Each module has a named owner role (e.g. @protocol-engineer, @ledger-owner). A merge gate (npm run test:gate) makes this enforceable rather than aspirational: it fails on any failing, skipped, or todo test, and it fails if the passing-test count ever drops below a floor recorded in code — so quietly deleting a test to "make it pass" is itself a build failure. Two modules (ledger, messaging) were deliberately left as throwing stubs rather than half-built, because a wrong ledger silently produces a wrong invoice — that risk needs a human owner, not more code.

The most distinctive part of the workflow is the independent review step: after a module lands, a separate pass audits it by actually running the code and reproducing every claim with a command — not by reading and trusting the code. Two of those reviews are the backbone of the quality section below.

The audit trail — evidence this wasn't just claimed, it was checked

Case study — Module 8 (Rules engine)

What happened: the first delivery of the rules engine was reviewed on 2026-09-01. The reviewer didn't just read the code — they tried to import it, and it threw a SyntaxError. Its own test file crashed before a single assertion ran. Three more real bugs were found underneath: a timezone bug that would fire false after-hours alerts depending on what server timezone it ran in, a threshold typo that was 60× too small, and a dedupe key that could silently drop real events.

What happened next: every finding was fixed, each with its own test, and the module was re-verified — 12/12 tests, wired cleanly into messaging. The finished module is now rated solid above.

This is the pattern worth trusting: problems get found by someone actually running the code and reproducing the failure, not glossed over — and then they get closed, not hidden.

Case study — Parser & handshake hardening

What happened: a second audit (2026-09-02) targeted the protocol parser and device handshake — the part of the system a stranger on the internet can actually talk to. It found the happy path was correct, but the defensive envelope around it had real gaps: no cap on a declared packet length (a peer could steer one connection toward ~4GB of memory), no socket idle timeout (a silent connection could be held forever — a textbook slowloris), and no codec/IMEI validation.

What happened next: all 6 meaningful findings were fixed the next day, each its own commit with its own test, raising the test-gate floor from 135 to 149 in the process. One item (signed-integer decoding) was correctly deferred — nothing in the system uses a signed parameter yet, so building it now would be speculative.

Known gaps & open risks — the honest list

  • high
    No TLS or per-device authentication on the ingestion port. Today the only gate is a valid, registered IMEI plus a per-IP rate limit. Fine for a private pilot; needed before this port faces the open internet.
  • high
    The ledger isn't wired to real billing yet. Correct against its spec and the seed scenario — but no real fleet's numbers have been reviewed by a human, and the physical hardware reconciliation step hasn't happened. Don't invoice off it yet.
  • medium
    Message delivery isn't durable yet. The dedupe log for WhatsApp sends lives in memory — a restart would currently risk re-sending already-delivered messages once a real sender exists.
  • medium
    Enrichment is intentionally thin. Coarse machine state only — no real trip segmentation yet, and the geofence rule does its own standalone distance check rather than a shared enrichment concept.
  • medium
    The ignition-duration billing basis has an open number. A device-offline gap currently has no default cap on how long it can be billed at its last known state — the production threshold (hours?) needs a human, business-side decision.
  • medium
    No real fleet has been named yet. Every per-machine CAN program number is still a candidate until the actual make/model/year list is confirmed — this blocks the hardware half of D1 below.
05

Is this safe to hand to the dev/test team?

Short answer

Yes, for internal development and testing. The foundation is genuinely solid: a real protocol implementation checked against Teltonika's own published test vector, 179 passing tests tied to named correctness rules (not vibes), green CI on a clean machine, graceful-shutdown behaviour proven on real OS processes, and — the strongest signal — a demonstrated habit of catching its own mistakes through independent review and actually fixing them, with commands and commits to show it.

Not yet for production billing or public internet exposure. Two specific things stand between here and that: (1) the ingestion port has no TLS/device-auth yet, and (2) the ledger has not been reconciled against a single real, physical machine. Neither is a sign of sloppy work — both are deliberately fenced off (throwing stubs, explicit "P2/P4" gates) rather than quietly shipped half-done.

How this compares to off-the-shelf telematics platforms

The honest question isn't "is custom software better" — it's what each option actually gives you control over. This system was built custom for one specific reason: nothing off-the-shelf hands you a tamper-evident, dispute-ready evidence chain over raw ECU data, scoped per tenant, with correctness invariants enforced as code.

The custom build stays the reference implementation and the test harness either way.

07

Getting real hardware talking to this — step by step

No physical unit has arrived yet, so here is the exact path from an empty box to a first real handshake in the logs, plus what you can do with software alone right now while you wait.

  1. Order the hardware

    A Teltonika FMC130 (or FMC920) tracker per machine, a data SIM with an M2M APN, and — only for machines whose engine hours need to be billed — a CAN adapter (LV-CAN200, ALL-CAN300, or CAN-CONTROL) matched to that machine's exact make/model/year via Teltonika's supported-vehicle list.

  2. Configure the device

    Using Teltonika's Configurator app: point the server address at wherever this ingestion server runs, on the TCP port it listens on (INGEST_PORT, default 5027). Set the codec to 8E. Set the AVL parameter list to include at minimum IO 239 (ignition), 240 (movement), 69 (GNSS status), and — if a CAN adapter is fitted — 102 (Engine Worktime) and 100 (CAN program number).

  3. Register the device before it connects

    The handshake only accepts IMEIs already in the device registry — add the unit's real 15-digit IMEI and model to src/store/seed-data.js (or the devices table under Postgres) first. Otherwise you'll see handshake_rejected reason=unknown_imei in the log and the connection is closed.

  4. Make the server reachable

    For a first bench test, run npm run start:ingest somewhere the device's SIM can actually reach — a public IP/port, or a TCP tunnel (e.g. a temporary ngrok tcp forward) if you're testing from a laptop behind NAT.

  5. Watch for the first real handshake

    A success looks like event=handshake_accepted imei=... model=... followed by event=packet_acked lines as it starts sending. A rejection names why: unknown_imei (not registered yet) or malformed_imei (not 15 ASCII digits — check the Configurator setting).

  6. Confirm the data lands correctly

    Query the read API with the right tenant header (see RUNBOOKS.md §3) and check positions are arriving, and — only for a CAN-mapped asset — that engine hours appear. A non-CAN machine correctly shows no engine hours; that's invariant 9 working, not a bug.

  7. Reconcile before you trust it as billing evidence

    This is the one step only physical access can do: read AVL 102 back through the Configurator or Traccar, and compare it by hand against that exact machine's own dashboard hour-meter. Only once they agree is that machine's data evidence, not just a reading — this is the last open piece of decision D1.

While you wait for hardware

You don't need to wait to exercise the software — the simulator speaks the identical real wire protocol, so nothing on the server side changes when a physical unit arrives. Run npm run sim:list to see what's available, then npm run sim -- --scenario handover for the most important story (one device changing tenants and machines mid-stream), or --scenario tamper to see how a pulled harness is handled.

08

Closing the simulator-vs-real-device gaps

Follow-up research on the six shortcomings flagged earlier: for each, what the outside world (Teltonika's own documentation, and standard resilience-testing practice) actually says, and whether it can be closed with tooling today or genuinely has to wait for a physical device.

Engine-hours data (AVL 102) is invented, not measuredstill hardware-only

What was found

Teltonika's own CAN-adapter documentation (covering LV-CAN200, ALL-CAN300, CAN-CONTROL — the exact three adapters this system targets) independently lists "Engine Work Time" and "Engine Work Time (counted)" as standard tracked parameters across their product line. That corroborates this project's own AVL 102-vs-103 split — it isn't a reading this team invented, it's how Teltonika's own adapters are documented to behave. The same page also flags that many CAN parameters "reset to zero when ignition is off," and that program numbers are 3-, 4-, or 5-digit depending on adapter firmware age (matching D1_CAN_ENGINE_HOURS.md exactly).

Recommendation

Nothing closes this without a physical install — but the vendor documentation raises one thing worth checking explicitly during hardware bring-up that the report didn't call out before: confirm "Engine Work Time" (AVL 102) is specifically the persistent lifetime meter and not one of the ignition-reset-to-zero parameters on the adapter/vehicle combination you end up buying. Add that as an explicit line item to reconcile()'s bring-up checklist.

Sources: Teltonika — FMC130 CAN adapters
No real cellular network behavior (loss, latency, mid-stream drops)closeable now, with tooling

What was found

Two mature, zero-hardware tools do exactly this. Linux's built-in tc netem can add packet loss, delay, and jitter straight onto a network interface (e.g. tc qdisc add dev eth0 root netem delay 100ms 20ms loss 2% approximates a poor mobile connection; delay 600ms loss 3% corrupt 0.1% approximates a satellite-grade link) — it even works against loopback for local testing. Toxiproxy (Shopify, open source) goes further: it's a proxy you put in front of the ingestion port that injects specific failure modes on demand — latency, timeout, bandwidth (to mimic a slow 2G/3G trickle), and — most relevant here — reset_peer, which drops a connection mid-stream exactly like a real dead zone would.

Recommendation

Add a Toxiproxy container in front of INGEST_PORT in docker-compose.yml, point the simulator at the proxy instead of the server directly, and script the existing scenarios (handover, day-cycle) to run once through latency+reset_peer toxics. This directly exercises the untested F6 timeout/idle-disconnect code against something closer to a real flaky link — a concrete new test suite, not a hardware requirement.

Sources: tc netem packet-loss guide Toxiproxy + Docker chaos testing
Firmware quirks — offline buffering / backlog behaviorpartially closeable

What was found

Teltonika's own data-acquisition docs confirm the mechanism this system already assumes: "Min Saved Records" sets how many records must accumulate before a send is attempted, and "Send Period" controls how often the device retries. That matches this harness's own model of one packet carrying multiple records. What the public documentation does not state precisely: the maximum on-device buffer capacity, or exactly how a large backlog is chunked into packets once connectivity returns.

Recommendation

Approximate it in software now: add a new simulator scenario — e.g. reconnect-backlog — that withholds records for a simulated gap and then sends a single oversized packet (bumping toward the existing INGEST_MAX_PACKET_BYTES cap) to prove the server handles a genuine backlog burst correctly. That closes most of the practical risk. The exact on-device buffer ceiling is a vendor-support question, not a code gap — worth a direct question to Teltonika alongside the D1 hardware questions already queued.

Sources: Teltonika — FMC130 Data acquisition settings
Reconnect storm at production scalealready closeable — mostly already built

What was found

Standard practice for this exact failure mode (many clients reconnecting simultaneously after an outage) is client-side exponential backoff with full jitter: each client waits random(0, min(max_delay, base × 2^attempt)) rather than a fixed schedule, so retries desynchronize instead of arriving in coordinated waves. This system's own src/tools/load-test.js already supports exactly the adversarial case — --ramp-ms 0 connects every simulated device in one burst rather than staggering them — and it's already been run at 1,000 connections with zero errors.

Recommendation

This is closer to a documentation gap than a capability gap: re-run the load test at a size that models a real fleet outage-recovery (e.g. 5,000–10,000 bursty connections) and record it as the explicit "reconnect storm" proof in TESTING.md, rather than leaving it implied inside the general load-test section. Separately, if a real device fleet's own reconnect logic isn't already jittered, that's worth confirming with Teltonika's firmware behavior — the server side is already proven to take the hit either way.

Sources: Exponential backoff with jitter, explained Thundering herd problem — background
Rate limiter assumes one IP = one device (breaks under CGNAT)closeable — small, specific code change

What was found

Carrier-grade NAT (CGNAT) really does put many mobile devices behind one shared public IP — standard on most cellular M2M networks. Cloudflare's own published research found IPs behind CGNAT get rate-limited roughly 3× more often than ordinary IPs specifically because of this collateral-damage effect: one bad actor's traffic gets a whole shared IP throttled, punishing every innocent device sharing it.

Recommendation

The fix doesn't need Cloudflare-scale ML classification — it needs the limiter to key on something CGNAT can't collapse. The device's own IMEI is readable the instant the handshake frame arrives, even for an unregistered IMEI. Change handshake-limiter.js to throttle on (sourceIp, imei) rather than sourceIp alone (keeping the IP-only limiter as a secondary, higher-threshold backstop against a genuinely malicious single source). That keeps one misbehaving device from getting every other device on the same carrier IP blocked.

Sources: Cloudflare — detecting CGNAT to reduce collateral damage

Net effect: of the six original gaps, four (network realism, backlog bursts, reconnect storms, CGNAT rate limiting) can be substantially closed with tooling and small code changes before any hardware purchase. Only the engine-hours reconciliation itself is an unavoidable hardware gate — everything else was a testing gap, not a hardware gap.

Open decisions only a human can make

    Name the real fleet. Exact make/model/year for every machine — every program-number row is a candidate until this is confirmed.

    Sign off the billing math against real fleet data. The ledger is correct against its spec; it still needs a human to review it against actual numbers before it backs an invoice.
