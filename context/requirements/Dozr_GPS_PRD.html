00How to read this PRD

This document specifies the GPS/telematics device-data layer only — the backend that receives data from Teltonika devices on construction machines, turns it into trustworthy records, and serves them to the dashboard. It is deliberately not about the Marketplace or Vendor OS; those are separate products with their own specs.

It sits in a set of four. Read this for what to build and to what standard; read the Build Handbook for who builds it and how the project runs; read CLAUDE.md for the invariants any coding agent must never break; read the Expert Build Review for the reasoning behind the architectural positions. Where they conflict, this PRD is authoritative on scope and requirements, and CLAUDE.md is authoritative on the correctness invariants.

01Goals & non-goals

The product exists to make construction-equipment utilisation measurable and billable from a machine's own engine data, and to give operators a live picture of where their fleet is and how hard it is working. Success is not "we can see dots on a map" — it is "we can put a number on an invoice and defend it."

Goals

#GoalMeasured by
G1Capture device data without lossZero acknowledged-then-lost records across a full pilot cycle
G2Produce billing-grade engine hoursUtilisation hours reconcile to the machine's own meter within tolerance
G3Make every billed number defensibleEach utilisation record resolves to sealed, immutable evidence
G4Light up the existing dashboard with real dataAll nine fleet-v2 screens serve live data, not mocks
G5Keep tenants isolatedNo tenant can read or be billed for another's assets — enforced & tested
G6Deliver alerts & reports where operators already areKey events reach the operator over WhatsApp

Non-goals (for this product / this phase)

  • Not the Marketplace or Vendor OS — those are separate products.
  • No phone- or app-based location tracking — tracking is hardware-only, by design.
  • No predictive analytics, ML, or driver-scoring at pilot — utilisation is arithmetic and rules, not modelling.
  • No native mobile app — delivery is WhatsApp plus the web dashboard.
  • No in-house SIM/MVNO or custom firmware — use the telco's M2M SIM and Teltonika's stock firmware.
  • No automated invoicing/payment in this layer — it produces the billable number and its evidence; billing itself lives elsewhere.

02Users & jobs-to-be-done

Four human roles and one non-human actor. The non-human one — the device — matters because it has a "job" the system must respect: deliver its buffered data exactly once and then be free to forget it.

UserTheir job-to-be-doneWhat the product owes them
Fleet operator / owner"Know where my machines are and how much they worked"Live map, utilisation per machine, alerts on their own fleet only
The party being billed"Trust — or challenge — the hours I'm charged for"A utilisation figure backed by defensible, inspectable evidence
Ops coordinator"Keep devices healthy and installs verified"Device health, last-seen, silent-device alerts, install verification
Dozr admin"Onboard tenants, devices, and assignments safely"Admin tools for tenants, device provisioning, dated assignments
The device (actor)"Hand off my buffered data exactly once, then forget it"An acknowledgement it can trust — sent only after durable storage

The device is a first-class user. Designing around its contract — buffer, send, wait for ACK, delete — is what separates a telematics system that can bill from one that merely maps. Treat its acknowledgement as a promise, not a formality.

03The product spine — five capabilities in order

Every requirement in this PRD serves one of five capabilities, and they depend on each other in strict order. You cannot attribute utilisation to an owner (capability 4) before you can detect that the machine was working (3), which you cannot do before you can reconstruct its history (2), which requires that you located and stored it losslessly in the first place (1). Evidence (5) wraps the whole chain so the output can be billed.

1LOCATEReceive and durably store every record a device sends — position, ignition, engine data. Lossless capture is the foundation everything else stands on.
2RECONSTRUCTTurn the stream into an accurate, gap-aware history of each machine — where it was, when, and in what state.
3DETECTInfer meaningful states from the history — moving, idle, working — and geofence entry/exit, explainably.
4ATTRIBUTEAssign each machine's activity to the right owner/renter for the right period, using dated assignment windows.
5EVIDENCESeal the utilisation figure and the chain behind it so it survives a billing dispute. This is the product's reason to exist.

Do not build these out of order, and do not skip ahead to the screens. A pretty dashboard on top of lossy capture (capability 1 done wrong) is worse than no dashboard, because it looks trustworthy while being wrong. The functional requirements that follow are grouped to build this spine bottom-up.

04Functional requirements — ingestion & device contract

Capability 1 (LOCATE). This is where correctness is won or lost: the device holds the only copy of its buffered data until the server acknowledges, so the acknowledgement must be a promise the server can keep.

IDRequirementPriority
FR-ING-1Accept TCP connections from Teltonika devices, complete the IMEI handshake, and admit only devices on the provisioned allowlistMust
FR-ING-2Parse Codec 8 and Codec 8 Extended (0x8E) frames; validate CRC-16; reject malformed frames without acknowledging themMust
FR-ING-3Acknowledge a frame only after all its records are durably persisted — never before. This is the system's foundational invariantMust
FR-ING-4Idempotent ingest: dedupe on (device, record identity) so a buffer re-sent after a missed ACK cannot double-countMust
FR-ING-5Persist the raw frame to immutable cold storage as part of durable write, to anchor the evidence chainMust
FR-ING-6Back-pressure under load: when storage lags, stop acknowledging rather than dropping — let devices hold their bufferMust
FR-ING-7Support TLS from device firmware 03.27.02+ (D9); optional mutual TLS with a device client certificate (D11)Should
FR-ING-8Support UDP transport as a fallback where TCP session cost is prohibitiveCould

FR-ING-3 is the requirement the whole product rests on. If the server acknowledges before the write is durable and then crashes, the device has already deleted its only copy — the data is gone, silently, and a billing period is now under-counted with no way to know. Everything else can be rebuilt; an acknowledged-then-lost record cannot.

05Functional requirements — decoding, data model & tenancy

Capabilities 2 (RECONSTRUCT) and part of 4 (ATTRIBUTE). Turning raw frames into a canonical, tenant-scoped, time-correct record — and being honest about what the device did and did not report.

IDRequirementPriority
FR-DEC-1Decode standard AVL fields: position, speed, GNSS quality, ignition, movement, and device I/OMust
FR-DEC-2Decode CAN engine data via the machine's program number (D1). When the make/model/year is unlisted, store position + ignition only and flag the asset "no engine data"Must
FR-DEC-3Normalise every frame into one canonical record schema — the frozen contract every downstream module and screen depends onMust
FR-DEC-4Label engine-hours source explicitly as ecu (from CAN) or estimated (derived). The two must never be merged in storage or on screenMust
FR-DEC-5Treat NULL as distinct from zero everywhere — "we didn't receive it" is not "it was zero"Must
FR-MOD-1Pooled multi-tenant schema with row-level security; every read and write is scoped to a tenant with no exception pathMust
FR-MOD-2Dated device→asset and asset→owner assignment windows; resolve each record against the assignment that was true at its own timestampMust
FR-MOD-3Store position history in a time-series hypertable; keep a hot last-state cache for the live mapMust
FR-MOD-4Keep the immutable raw layer physically separate from the derived, queryable layerShould

Why FR-MOD-2 is subtle and load-bearing: a machine changes hands mid-month, and both parties must be billed only for their own window. Resolving assignment at query time (or "as of now") silently misattributes the handover period. Every record must be attributed using the assignment that was in force at the moment that record was produced — not the current one.

06Functional requirements — enrichment, rules & the nine screens

Capability 3 (DETECT) plus the surfaces. The nine fleet-v2 screens already exist as UI on mock data; the requirement here is to feed them real, honest data — including honest empty, stale, and error states.

The dashboard is already built. The work here is not design — it is data contracts and honest states. The two screens that must be right for the pilot are Fleet Map (proves LOCATE + DETECT) and Utilisation (proves the billable number). The rest can follow.

07Functional requirements — utilisation ledger & evidence chain

Capabilities 4 (ATTRIBUTE) and 5 (EVIDENCE). This is the product's reason to exist: a billable number that survives a dispute. The highest-stakes module in the system.

IDRequirementPriority
FR-LED-1Compute utilisation (working engine hours) per machine per period from ecu hours. The ignition-counter fallback is never admissible as billing evidenceMust
FR-LED-2Attribute each period's utilisation to the correct owner/renter via the dated assignment window (FR-MOD-2)Must
FR-LED-3Produce an immutable, sealed utilisation record per machine per billing periodMust
FR-EVID-1Each sealed record links to the underlying raw frames; integrity is provable via hash/manifest (tamper-evident)Must
FR-EVID-2Retain evidence for 7 years in immutable cold storageMust
FR-EVID-3Dispute pack: given any utilisation figure, produce its complete evidence trail on demandMust
FR-EVID-4Anchor the manifest to a trusted time source so "when" is provable, not just asserted (D10)Should

What "billing-grade" means, concretely: if a customer says "you charged me for 40 hours, prove it," the system must return the sealed record, the engine-hours source (ecu, not estimated), the assignment window that put the machine on their account, and the raw frames behind the number — all demonstrably unchanged since sealing. A number you cannot defend this way is not billable, no matter how accurate it happens to be.

08Functional requirements — messaging & admin

Delivery where operators already are (WhatsApp), and the administrative surface that keeps tenancy, devices, and — critically — assignment windows correct, since those drive billing attribution.

IDRequirementPriority
FR-MSG-1Deliver key alerts to operators via WhatsApp (Cloud API), using pre-approved message templatesShould
FR-MSG-2Scheduled utilisation / activity reports via WhatsApp or emailShould
FR-MSG-3Two-way queries — operator asks fleet status over WhatsApp and gets a replyCould
FR-ADM-1Tenant onboarding — create org, users, and rolesMust
FR-ADM-2Device provisioning — register IMEI, bind to tenant, and set dated assignment windowsMust
FR-ADM-3Device health view — last-seen, buffer state, CRC/reject rate, and the install-verified flagMust
FR-ADM-4Audit log of admin actions — especially assignment changes, since they move billing attributionShould

"Install-verified" is a first-class field, not a note. Per the handbook, a device is only "installed" once engine hours have been seen arriving from that machine. FR-ADM-3 makes that a tracked state the ops coordinator manages — not a comment in a spreadsheet.

14Out of scope

Explicitly not part of this product or this phase — recorded so scope creep has to argue its way in.

  • Marketplace and Vendor OS — separate products; this is the device-data layer only.
  • Automated invoicing & payment — this layer produces the billable number and its evidence; billing runs elsewhere.
  • Predictive analytics / ML / driver scoring — utilisation here is arithmetic and explainable rules.
  • Native mobile app — delivery is WhatsApp plus the web dashboard.
  • Phone / app-based location — tracking is hardware-only, by design.
  • In-house SIM/MVNO or custom firmware — use the telco's M2M SIM and stock Teltonika firmware.
  • Custom Go ingestion gateway — a P6 migration triggered only when engine hours bill externally, not pilot scope. Start on Traccar.
