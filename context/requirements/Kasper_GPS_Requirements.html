GPS Requirements

What the initial release contains, stated so it can be estimated against and tested. One hundred and twelve numbered requirements, each with an acceptance condition, plus what is explicitly excluded.

00Purpose and how to use this

This exists to answer one question that has been asked and not yet answered in writing: what does the initial release contain? An estimate produced without it is a guess about scope dressed as a guess about effort.

How to respond to it

Do not respond with a total. Respond per requirement group: rough effort, any requirement you think is wrong or missing, and anything you cannot estimate without more information. A requirement you disagree with is a useful answer — an estimate that silently absorbs it is not.

Where a requirement seems obvious, check its acceptance condition before agreeing. Several of them look ordinary and are not: ING-04, ATT-05, EVD-03 and DET-10 in particular describe behaviour that most systems get wrong by default.

These are requirements, not a design. Where one implies a mechanism it is because the mechanism is the requirement — acknowledging only after a durable write is not an implementation preference, it is the difference between a gap being recoverable and being invisible.

01Scope boundary

The initial release delivers five capabilities in dependency order. Everything in this document serves one of them; anything that served none has been cut, and the cuts are listed in section 15.

CapabilityMeansDone when
LocateWhere is this machine now, and is it workingAn operator finds any asset in scope on a map and knows whether the answer is current
ReconstructWhere has it been, and what did it doA day can be replayed accurately, including a day containing an outage
DetectTell someone when something mattersA real geofence crossing reaches a real phone, and a silent device raises an alert
AttributeWhose machine was this, and whenA record resolves to exactly one tenant at its own timestamp, enforced at the data layer
EvidenceProve how long it ran, months laterA hire period produces a sealed record, backed by immutable data, that discloses its gaps

Where the difficulty actually sits

Locate, reconstruct and detect are satisfied by any competent tracking product and account for most of the visible surface. Attribute and evidence are the reason this is being built rather than bought, and they account for almost none of the visible surface. An estimate that scales with screens will be wrong in both directions at once.

02Conventions

PriorityM in the initial release · S wanted, may be deferred with agreement · C out unless it costs nothing

Source matters for estimation. A CAN-sourced requirement carries an external dependency that may not be satisfiable for every machine; a Design-sourced requirement cannot be added later without rework. Neither is visible from the requirement text alone.

ING-04 is the requirement to read twice

The device deletes its only copy of a record the moment it is acknowledged. Acknowledging before the write is confirmed converts a crash into silent, permanent data loss — and the loss is invisible, because a gap looks exactly like a machine that was switched off. Everything in EVD depends on this being right, and it cannot be added afterwards.

Why ATT-03 and ATT-04 are two tables and not one

A device moves to a different machine when it fails or the machine is sold. A machine changes hands every time it is re-hired. These happen on different schedules and both are dated, so telemetry has to resolve through both to answer whose engine hours these are, on which asset. Collapsing them into one relationship is the single most common way this class of system is got wrong, and the failure is silent until a customer sees another customer's data.

DET-10 and DET-11 are the two that get missed

A device going silent cannot be detected by anything arriving, because the defining feature is that nothing arrived — so absence-based rules need a scheduled sweep. And a device replaying an outage will regenerate every geofence crossing it missed; without a staleness threshold those all get delivered, hours late, to somebody's phone.

EVD-07 and EVD-08 together

When a machine is offline the system knows nothing — it does not know the machine was idle. Recording that time as idle understates usage on a record somebody relies on. The requirement is to carry the unobserved time explicitly and show it, which is uncomfortable and correct. A record that quietly absorbs its gaps is worse than one that admits them.

13Interfaces between the two teams

Kasper owns the hardware track — vendor relationship, procurement, SIMs, installation. The development team owns the software. These are the handoffs. Each needs an owner and a date, or it will be discovered late.

IDInterfaceDirection and what it blocks

INT-03A traffic generator producing valid Codec 8 and 8E framesDev team, internal. Unblocks their schedule from hardware procurement
INT-04An install verification view showing first ECU reading per deviceDev team → Kasper. Blocks sign-off of any installation
INT-05Fleet list with make, model, year and CAN program number availabilityKasper → dev team. Blocks the asset model and ATT-02

INT-08The telemetry record shape, agreed jointly and owned by KasperBoth ways. The interface between the two tracks

INT-03 is the one worth doing first

A traffic generator producing valid frames removes the development team's dependency on our procurement entirely. It is also the only practical way to test outage replay, duplicate delivery and clock skew on demand, since none of those can be produced reliably by a real device. Built early, it unblocks the whole software track and makes ING-06 through ING-09 testable before a single machine is instrumented.

16Acceptance

Six demonstrations. Not a document review — someone watches each of these happen.

#DemonstrationCloses

Demonstration 2 is the one to insist on

It takes an afternoon, it tests the property the entire architecture is built around, and it is the only one that cannot be faked with convenient data. A team that resists it is telling you something.

18How to estimate against this

  1. Estimate per group, not in total. Eight functional groups plus non-functional. A total hides which group you think is hard, and that is the information worth having.
  2. Estimate the acceptance condition, not the requirement text. Most of these are ordinary to build and awkward to demonstrate. The demonstration is the deliverable.
  3. Flag every requirement you disagree with, and every one you would rather not build. Disagreement is a useful answer. Silent absorption is how estimates become fiction.
  4. Say what you cannot estimate yet, and what would let you. Several of these depend on device behaviour nobody has observed; the honest answer is a range plus what would narrow it.
  5. Separate first-time-through work from ongoing. Retention, monitoring and backup are not one-off tasks.
  6. Tell us what is missing. This is a first pass by people who have not built one of these before. A requirement we have not thought of is more valuable than a tighter number on the ones we have.
