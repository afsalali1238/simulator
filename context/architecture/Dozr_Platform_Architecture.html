00How to read this, and what changed

This document is the Dozr successor to Kasper Architecture v3. That document was accurate about the system it described and is still the best record of the .NET platform's internals — but as a picture of Dozr it has three problems, and this version exists to fix them.

ChangeWhat and why
AddedThe job pipeline. v3 described a B2B commerce platform with carts, product galleries and reports. That is the shape of the software, not the shape of the business. Dozr's actual product is a 13-stage operational pipeline from booking to payment — section 09 — and no architecture document that omits it can be used to make decisions.
AddedWhatsApp as a first-class channel. v3 mentions email via Razor templates and nothing else. In reality quotes, approvals and job updates happen on WhatsApp; the current Marketplace build has no backend at all and uses wa.me deep links by design. A channel that carries the commercial workflow belongs in the architecture.
AddedMulti-tenancy as a dated relationship. v3 handles tenancy as "role-aware queries filter by currentUser". That is sufficient for a commerce app and insufficient for rented assets that change hands — section 12.
AddedThe telematics layer and its integration points, absent from v3 entirely.
AddedEnvironments, NFRs, a risk register and a document map. v3 has none of these, which is why its readers cannot tell what is decided from what is assumed.
RemovedComponent-level implementation detail. v3 §4 names Index.vue, ReportBody, apiStateStore.fetchCart. Source files drift within weeks of being written into a document; this version describes contracts and boundaries and lets the code describe itself.
RemovedElasticsearch and Kibana as assumed infrastructure. Kept in section 06, but demoted to a question. At Dozr's catalogue size Postgres full-text search is adequate, and an Elasticsearch cluster is a standing operational cost that has to earn its place.
RemovedGuest checkout and cart semantics as core concepts. Dozr's equivalent is an RFQ, and an RFQ is not a cart — it has no price until a vendor quotes.
Corrected"Microservices." v3 calls the architecture microservices-based. Three deployables sharing two databases behind one ingress is a small service-oriented deployment, and calling it microservices invites decisions — per-service datastores, independent release trains — that the team is not staffed for. Named accurately in section 05.

01Overview

Purpose. Dozr is a UAE construction and port logistics platform. It rents equipment, books freight, and gives the vendors who own that equipment the software to run their side of the job — with GPS and engine data underneath, so that what was delivered can be proven rather than argued about.

Three products, one platform

Marketplace Live

Client-facing. Browse equipment and freight, request a quote, approve it, track the job, receive proof of delivery. Currently a static multi-page site with WhatsApp deep links in place of a backend.

Vendor OS + Ops Live

Two faces of the same pipeline. Ops runs the job board internally; Vendor OS is the vendor's own view — their assets, their quotes, their jobs, their invoices.

Fleet / Telematics Rebuild

Seven-screen internal dashboard over live device data: map, fuel, maintenance, geofences, utilisation, cost and ROI, reports. The evidence layer for everything else.

Architectural style, stated honestly

A pipeline-centric platform with a thin client tier and a shared operational datastore. The organising principle is not the service boundary — it is the job. A job moves through thirteen stages; every product is a different actor's view of that same job, and every integration exists to move a job forward or to prove something about it. Design decisions are correct when they make a stage transition cheaper, auditable, or harder to get wrong.

The one thing to hold onto

Dozr's defensibility is not the catalogue and not the dashboard. It is that a job's history — who quoted what, when the machine arrived, how many hours it ran, what was signed for — is captured as it happens and can be produced later. Every architectural choice in this document is downstream of that.

02Two systems, one platform

There are currently two codebases that both legitimately claim to be "the platform". Documenting only one of them is how teams end up building the same feature twice.

The position

System B is the target. System A is the reference implementation and the fallback, not the enemy. The rebuild is justified by operating cost and iteration speed, not by any technical failing in the .NET platform — and several things System A does correctly are things System B has not yet had to solve: voucher numbering under concurrency, audit stamping on every write, per-endpoint authorisation, decoupled read projections. Those are requirements, not legacy.

The migration trap to avoid

The failure mode here is not choosing wrong — it is choosing neither, and running both indefinitely with the pipeline half in each. A job that exists as an RFQ in SQL Server and as a row in Supabase has two truths and no reconciliation. Pick one system per pipeline stage, migrate whole stages, and write down the date each one moved. Section 14 sets out the cutover discipline.

04Client layer

4.1 Marketplace Live

Multi-page static site — index, browse, equipment-detail, freight, cart, wishlist, tracking, quote-approval, orders, plus auth and content pages. Vanilla HTML/CSS/JS, no framework, no build step. Brand tokens are CSS custom properties in one shared stylesheet.

No backend for v1, by design. Equipment data is a JavaScript module; every action that would need a server opens a WhatsApp deep link. This is not a stub — it matches how the business actually runs quotes and approvals today. The data-access functions are the seam: Supabase gets wired in behind them without touching page markup.

4.2 Ops console Live

Internal job board: enquiries, a stage-based Kanban, vendor and equipment masters, job detail, invoicing, reports. Reads and writes Supabase directly from the browser via the JS client. Sign-in is currently short-circuited — see section 13, this is the platform's most serious open issue.

4.3 Fleet dashboard Rebuild

Seven screens — Fleet Map, Fuel, Maintenance, Geofences, Utilisation, Cost & ROI, Reports — rebranded onto Dozr tokens, running on mock data shaped to match the eventual telemetry contract. Deliberately kept on an independent stylesheet so it can evolve separately from Marketplace.

4.4 Vendor OS Next

Not yet rebuilt. The vendor's own view of the same pipeline: their assets, incoming RFQs, quotes submitted, jobs won, documents, invoices, payment status. Treat it as a permission scope over the existing Ops surfaces rather than a separate product, and most of it is configuration rather than new screens.

4.5 Shared client conventions

  • Brand tokens are non-negotiable and live in one place per product. Ink, yellow, canvas, slate, line, green, error; Space Grotesk / Hanken Grotesk / Space Mono. A colour outside that set is a bug.
  • Accessibility is a gate, not a pass. Real <button> elements, labelled inputs, AA contrast, keyboard reachability — already enforced on Marketplace and expected of every new surface.
  • Mobile-first. The site team on a phone in the sun is the primary reader, not the desktop buyer.
  • No secrets in client code. Stated here because it is currently violated — section 13.

05Application layer

5.1 System A — clean architecture in .NET

Four projects with enforced dependency direction. This is the part of v3 worth preserving verbatim, because it is a correct description of a sound structure:

ProjectHoldsMay depend on
Dozr.DomainEntities, value objects, projections, repository interfaces, enums, shared contractsNothing
Dozr.ApplicationServices, DTOs, validators, mapping profiles, email and view rendering, workflow orchestrationDomain
Dozr.InfrastructureEF Core DbContext, repository implementations, search integration, DI wiringDomain, Application
Dozr.APIComposition root, controllers, middleware, auth, CORS, health checks, OpenAPIAll of the above

Controllers never touch data access. Application services orchestrate, validate and map. Infrastructure implements the interfaces Domain declares. Request flow: Controller → Application service → repository interface → repository implementation → EF Core → SQL Server.

Three patterns worth keeping whatever else changes

  • Read projections separate from entities. Report and list views are their own shapes, built by explicit queries. This is what stops list endpoints from dragging entity graphs across the wire and generating N+1 queries.
  • Centralised audit stamping on the persistence hook, so created/modified metadata is consistent across every entity and cannot be forgotten at a call site.
  • Voucher numbering as a server-side concern, derived from configured settings and the last issued number. Document numbers are commercial identifiers; they cannot be generated client-side, and concurrency here is a correctness problem, not a performance one.

5.2 System B — Supabase, and its missing tier

Today the browser talks to PostgREST directly. There is no application tier. That is genuinely fine for CRUD over masters — and genuinely not fine for anything with a rule attached.

ConcernDirect-from-browser?Where it must live
Read a catalogueYesPostgREST + RLS
Create/edit mastersYes, once RLS is onPostgREST + RLS
Stage transitionNoEdge function — legal transitions, required artefacts, audit entry
Voucher / document numberingNoDatabase function under a transaction
Vendor cost vs client priceNoNever in a client-readable row. Margin is not the client's business.
Sending WhatsApp / emailNoEdge function — provider credentials never reach the browser
Invoice and payment writesNoEdge function with audit

Minimum viable server tier: a small set of Supabase edge functions covering stage transitions, document numbering, outbound messaging, and invoice writes. Everything else can stay direct. This is a few hundred lines, not a rewrite, and it is the difference between a prototype and a platform.

On the word "microservices"

Neither system is a microservices architecture, and neither needs to be. System A is three deployables sharing two databases behind one ingress; System B is a static site and a managed Postgres. Both are appropriate. Describing them as microservices imports expectations — per-service datastores, independent release trains, service discovery, distributed tracing — that would add cost without adding capability at this size.

06Data layer

6.1 Operational schema — System B

Eight tables carry the pipeline today: staff_profiles, vendors, equipment, rfqs, rfq_vendor_quotes, jobs, invoices, escalations, plus Storage buckets for equipment images and job documents. The shape is right. Four things are missing before it can carry the whole pipeline:

MissingWhy it matters
clients / tenantsThere is no client entity — jobs carry a client as loose fields. Without it there is no tenant to scope by, no client portal, and no way to answer "everything for this contractor".
assets + dated assignmentequipment is a vendor's listing. A telemetry-bearing physical asset with a dated hire history is a different thing. Section 12.
job_eventsAn append-only log of every stage transition with actor, timestamp and artefact. Today stage lives as a single mutable column, so the job's own history is unrecoverable — which is exactly what a dispute asks for.
documentsPO, ePOD, delivery note, invoice as first-class rows with a storage pointer, a hash and an issue date — not files loosely associated with a job.

Vendor cost and client price must not share a readable row

equipment.day_rate is annotated in the schema as internal-only, and jobs carries vendor cost. With RLS off and the anon key public, Dozr's margin on every job is currently readable by anyone who opens the browser console. This is a commercial exposure, not just a security one — and it is a design problem as much as a configuration one: cost and price should live in separate tables with separate policies, so that "internal only" is enforced rather than annotated.

6.2 Telemetry store

Separate from the operational database, by access pattern and by volume. Hot current-state per asset, warm history for playback and reports, cold immutable evidence. Fully specified in the companion GPS Build Handbook and PRD; the store choice is open and is tracked there.

6.3 Search — a question, not a component

System A runs Elasticsearch for catalogue search and Kibana for log visualisation. Before either is carried into System B, both should have to justify themselves. Dozr's catalogue is in the hundreds of items, not the millions; Postgres full-text search with a trigram index covers "excavator 20 ton Jebel Ali" comfortably, at zero additional operational surface. A search cluster is a standing cost, a scaling story and a failure mode — worth it at a volume Dozr does not have yet.

Recommendation: Postgres FTS in System B; revisit when catalogue search latency or relevance is an observed complaint rather than an anticipated one. Keep structured logging regardless — that requirement is real, the specific tool is not.

Notification routing

One rule, applied everywhere: an event fires a notification intent; a router decides channel and recipient; each attempt is recorded separately. One row per intent, one row per channel attempt with provider message ID and status. Retries are per attempt — a WhatsApp failure must never re-send the email. Without this the same alert arrives three times, or silently not at all, and nobody can tell which.

Contracts

  • Money as a decimal with an explicit currency; AED throughout; never a float.
  • Timestamps in UTC on the wire, rendered in Asia/Dubai. The platform runs in one timezone today and will not forever.
  • Errors carry a stable machine-readable code plus a human message. The code is the contract; the message is UI copy.
  • Idempotency keys on any write that a retry could duplicate — quote submission, invoice creation, payment recording.

Three rules that follow from the pipeline

  • Stage is a log, not a column. Every transition is an append-only job_events row with actor, timestamp, and a pointer to the artefact. The current stage is derived. A mutable stage column destroys exactly the history a dispute needs.
  • Every transition names its required artefact. You cannot reach stage 7 without an approval at stage 6, or stage 13 without an ePOD at stage 12. Enforce it server-side; a Kanban card that can be dragged anywhere is a data-quality problem waiting to happen.
  • Stages 10 to 12 are where telematics stops being a product and becomes evidence. That is the integration that matters — not the live map, which is a nice demo.

Note on the ops board. The live Kanban runs a simplified 7-stage view of these 13. That is correct — an ops board should show the transitions a human drives, not every system-generated one. Keep the 7 stages as a presentation grouping over the 13-stage log; do not simplify the log itself to match the board.

10Key flows

10.1 RFQ to approved quotation

1
ENQUIRYClient submits from Marketplace or messages on WhatsApp. Ops qualifies: equipment type, dates, site, access constraints, whether transport is included.
2
SHORTLISTOps selects candidate vendors by category, availability and site proximity. Availability comes from equipment.availability_status, which is only as good as the last vendor update — an honest weakness until Vendor OS makes updating it worth the vendor's time.
3
RFQ OUTOne RFQ record per vendor, issued over WhatsApp and email. Each carries a document number generated server-side.
4
QUOTES INVendor costs recorded against the RFQ. Cost is internal. It is never present in any row a client-scoped query can reach.
5
QUOTATIONOps applies margin and issues the client quotation, traceable to the RFQ it came from. Emailed as the document; WhatsApp carries the notice and the approval link.
6
APPROVALClient approves via the shared link. Recorded with timestamp, identity and the exact quotation version approved. This is a commercial commitment — version it, do not overwrite it.

10.2 Dispatch to GPS-verified delivery

1
ASSIGNVendor confirms asset and driver. The asset assignment window opens against the job's site geofence — this is the record that later attributes engine hours to this client and this contract.
2
TRACKLive position on the client's tracking page; ETA derived from position and route.
3
ARRIVEGeofence entry stamps arrival — replacing a phone call with a fact. Notification to client and ops.
4
EXECUTETime on site and engine hours accrue against the job. Idle time separated from productive time.
5
ePODSignature captured and bound to verified position and timestamp. A signature alone proves someone signed; a signature bound to a geofenced position and an engine-hours reading proves the delivery.
6
DEPARTGeofence exit stamps departure. Assignment window closes; the utilisation period is ready to seal.

10.3 Monthly Utilisation Certificate

The document the telematics layer exists to produce. For a hire period it states engine hours at start and end, the delta, idle hours, distance, and the source of each figure — ECU-read or estimated, never blended. It resolves through the dated assignment window, so the hours belong to exactly one client for exactly one contract over exactly one period, and it carries a pointer to an immutable evidence object.

Once issued, a certificate is sealed. Corrections are new documents that reference the old one. A reissued certificate must be byte-identical to the original, which means it renders from the sealed period record rather than from a live re-query.

10.4 Reporting

Two shapes, as in System A and worth keeping: summary, one row per document header — number, date, status, totals; and detailed, item-level with rates, amounts, discount and VAT. Filterable by date, client, vendor, item, item type and role, with role-based scoping applied server-side. Export as CSV and PDF. Scheduled delivery is a later phase; the scoping is not.

Recommendation — A then C, and drop B

Run the pilot on Traccar. It removes months of parser work from a solo build, it validates the hardware, the installation, the SIM and the CAN program numbers — which is where the pilot's real risk sits — and it produces the data history that every later decision depends on. Treat it as scaffolding with a known replacement date, and write the dashboard against our own contract rather than Traccar's REST shapes, so the swap is a data-layer change.

Build path C when engine hours start settling invoices, not before. The custom gateway's justification is acknowledge-after-durability and dated tenancy — real requirements, but requirements that bite at the point where the data becomes billing evidence, not at fifty pilot devices.

Path B is the weakest of the three and should be retired as a proposal. It carries the cost of a custom bridge and the cost and lock-in of a managed broker, while landing between A and C on integrity. IoT Core earns its place when devices speak MQTT natively and you want Shadow, Jobs and fleet provisioning — none of which applies to a Teltonika estate whose firmware is managed by Teltonika's own FOTA service.

12Multi-tenancy and identity

Pooled multi-tenancy: one platform, one database, row-level isolation. Not per-customer infrastructure. The reason is commercial — revenue is per device and per job, customers are many and small, and a fixed cost per tenant makes a five-truck vendor loss-making before hardware.

12.1 Why assignment is dated

An excavator works for one contractor this quarter and another next. If tenancy is a foreign key on the asset, then re-hiring the machine either rewrites history or exposes the previous client's data. Neither is acceptable when engine hours settle invoices.

assets            (asset_id, type, make, model, serial, owner_vendor_id)
devices           (imei, model, firmware, iccid, status)

device_assignments   -- which box is on which machine
  (device_imei, asset_id, from_ts, to_ts NULL)

asset_assignments    -- whose machine it is, and when
  (asset_id, tenant_id, project_id, site_id, from_ts, to_ts NULL, contract_ref)

Telemetry resolves to a tenant through both windows at the record's own timestamp. A denormalised tenant_id may be stamped for query speed, but authorisation never reads it — records arrive late and assignments get corrected retrospectively, so the stamp can be stale where the window cannot.

Enforce at the database, not in the query. Postgres row-level security fails closed; an application WHERE clause fails open the first time someone adds an endpoint and forgets it. The policies are already written in migration 0001_init.sql — the work is turning them back on, not authoring them.

One competitive-integrity rule deserves naming because it is easy to miss: vendors bidding on the same RFQ must not be able to see each other's quotes. That is a policy on rfq_vendor_quotes, and getting it wrong destroys vendor trust permanently.

13Security

Open finding — the Ops console has no access control

Migrations 0003_temp_open_access.sql and 0005_temp_open_storage.sql grant the anonymous role full read and write on vendors, equipment, rfqs, rfq_vendor_quotes, jobs, invoices, escalations and the image bucket. The anon key is published in client JavaScript. The migration comments say this plainly and flag it as build-only — the decision was deliberate and correctly documented. It is recorded here because the exposure is larger than "no login screen":

  • Vendor day rates and Dozr's margin on every job are readable by anyone with the URL.
  • Vendor trade licence and insurance expiry — commercially sensitive third-party data — are readable.
  • Every table is writable. Invoices and job records can be altered or deleted by an anonymous caller.
  • An unlisted URL is not access control. Vercel deployment URLs are enumerable, and the anon key is in the page source of a site that is publicly reachable.

This is the single highest-priority item in this document. Restore the 0001_init.sql policies, put a real sign-in in front of Ops, and rotate the anon key. Until then, treat everything in that database as public.

13.1 Identity

  • Staff and vendor accounts authenticate; JWT carries role and tenant claims. Clients may browse the catalogue unauthenticated but cannot see a job, a quote or a document without a session or a signed link.
  • Shared approval links are credentials. The quote-approval flow is a link sent over WhatsApp. Give it a signed, expiring token scoped to one quotation, and record the approving identity. A guessable or permanent link is an authorisation bypass on a commercial commitment.
  • Guest identity, as System A handles it, is a reasonable pattern for pre-account enquiries — a generated identifier that later merges into a real account. Keep it, scope it tightly.

13.2 Data protection

  • Vendor cost and client price separated at the table level, not by convention.
  • Trade licences, insurance certificates and Emirates ID scans in object storage under authenticated, time-limited URLs — never public buckets.
  • Encryption at rest on every store; TLS everywhere including internal hops.
  • Secrets server-side only. Provider credentials for WhatsApp, email and maps never reach client code.

13.3 Audit

Centralised created/modified stamping on every entity — System A's SaveChanges hook is the right pattern and its Supabase equivalent is a trigger. Beyond that: every stage transition, every document issued, every cross-tenant admin access, and every permission change is an append-only audit row. Audit is not logging — logs are for debugging and rotate; audit is evidence and does not.

14Deployment and operations

14.1 Environments

Gap There is currently one Supabase project. Preview deploys and local development point at the same database as production, which means a seed script or a careless delete is a production incident. Splitting dev from production is a half-day of work and should happen before the RLS fix, not after.

14.2 Deployment

  • System B: Vercel static hosting, git-push deploys, rewrites mapping / to Marketplace and /ops to the ops console. No build step. Rollback is redeploying a previous commit.
  • Database changes are numbered SQL migrations applied in order — the existing convention. Keep it, and keep migrations forward-only with an explicit note when one supersedes another, as 0003 already demonstrates.
  • System A: containerised, Kubernetes-deployed, ingress-routed, stateless API pods scaled horizontally. Per-environment configuration for database, JWT, CORS and origins.

14.3 Observability

Structured logging with request correlation, standardised error reporting, and health checks — all present in System A and all absent in System B, where a static site plus PostgREST produces almost no operational signal. Minimum for System B before it carries real jobs: edge-function logs with correlation IDs, an uptime check on the ops console, and an alert when a stage transition fails.

14.4 Migration discipline

The rule from section 02, made concrete: migrate whole pipeline stages, one at a time, and record the date each moved. For each stage — which system owns it, what the cutover was, and what happens to in-flight jobs. A stage half-migrated is two sources of truth, and the reconciliation cost exceeds the migration cost.

16Design decisions

#DecisionStatusRationale and cost
AD-1Vanilla HTML/CSS/JS, no build step, for the rebuildDecidedConsistent with three existing MVPs; fastest for a solo build. Cost: no component model, so shared UI is copy-paste discipline.
AD-2WhatsApp deep links instead of a backend for Marketplace v1DecidedMatches how quotes actually happen. Cost: nothing is tracked, retried or audited. Replace per stage as the server tier arrives.
AD-3Pooled multi-tenancy with dated assignmentDecidedCommercial: revenue is per device, customers are small, assets change hands. Isolated deployment stays available as a priced premium tier.
AD-4Postgres RLS as the tenancy boundaryDecidedFails closed. Currently disabled — section 13.
AD-5Job stage as an append-only event logProposedThe mutable stage column loses the history a dispute needs. Cost: one table and a derived-state read.

AD-7Traccar for the telematics pilot, custom gateway when hours billProposedSection 11.2. Removes months from the pilot; write the dashboard to our own contract so the swap is a data-layer change.
AD-8Postgres FTS instead of ElasticsearchProposedCatalogue is hundreds of items. Revisit on observed complaints, not anticipated scale.
AD-9Vendor cost and client price in separate tablesProposedMakes "internal only" enforceable rather than annotated.

19Glossary

TermMeaning
RFQRequest for quotation. Issued by Dozr to vendors. Has no price until a vendor answers — which is why it is not a cart.
QuotationThe priced document Dozr issues to the client, derived from vendor quotes with margin applied.
POPurchase order. The client's commitment, linked to the quotation it came from.
ePODElectronic proof of delivery — signature bound to a verified position and timestamp.
Utilisation certificateMonthly statement of engine hours, idle time and distance for a hire period, sealed and evidence-backed.
Assignment windowThe dated record of which tenant an asset belonged to over a period. The basis of both access control and billing attribution.
Pooled tenancyOne shared platform with row-level separation, as opposed to per-customer infrastructure.
RLSRow-level security. Access rules enforced by the database rather than by application queries.
Codec 8 / 8ETeltonika's binary format for a telemetry record.
CAN busThe machine's internal data network. The CAN adapter reads engine hours, fuel and fault codes from it.
Program numberThe Teltonika configuration identifying how to decode a specific machine make, model and year. Per-model, not universal.
TraccarOpen-source GPS server that already speaks Codec 8E. Proposed as the pilot ingestion path.
Bridge / gatewayCustom software that terminates device connections and translates their binary format. Not part of any managed AWS service.
System A / System BThe .NET/Vue platform in production, and the vanilla + Supabase rebuild replacing it.
