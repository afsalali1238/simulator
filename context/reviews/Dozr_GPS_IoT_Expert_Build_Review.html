01Verdict in brief

If you read nothing else, read this.

The plan is roughly the right length

Four to five months to a validated pilot is realistic. The team's five-month estimate is not the problem.

But the team is ~5× too large

Nine people for a ten-device pilot is a staffing template, not a plan. Two engineers plus a part-time coordinator fits the work.

The hard part isn't software

The critical path is physical — confirming CAN program numbers, procuring devices, and getting an auto-electrician onto real machines. No amount of code shortens it.

You should probably buy the hard tier

Terminating the Teltonika protocol is a solved problem sold as a service. Adopt it; own only the data model and the evidence path.

The six things that decide this project

  1. Engine hours are evidence, not a metric. They settle billing disputes, so they must be read from the machine's ECU, stored tamper-evidently, and never inferred. This one requirement constrains the entire design — it is why you cannot just buy an off-the-shelf tracking app and be done.
  2. The device speaks binary TCP, not MQTT or HTTPS. That single fact rules out pointing the fleet straight at a managed IoT cloud, and it is the fork your team's plan and your architecture doc quietly disagree on (section 04).
  3. Not every machine can produce engine hours. It depends on a Teltonika program number existing for that exact make, model and year, and on the machine broadcasting the value. Until that list is checked against your real fleet, the pilot's scope is unknown. This is the single most urgent open item.
  4. Adopt the protocol terminator; don't build it. Open-source and commercial servers already parse Codec 8E in production. Build your own only when engine hours start billing an outside party — and even then, only the terminator, not the platform.
  5. Keep the telemetry contract yours. One agreed record shape that everything downstream reads. It is what lets you change tools — or suppliers — later without a rewrite. Give it away and every future change needs whoever built it.
  6. The physical track starts now, in parallel, and sets the date. Program-number enquiry out this week; two test units on order this week. Neither waits on the software plan being agreed.

The one-sentence version

The problem is well understood in this repo; the risk is that it gets built as a nine-person cloud-software project when it is really a two-engineer integration whose real bottleneck is an electrician's calendar — so buy the ingestion, own the evidence, and start the hardware track today.

03What building this actually means

Strip away the product language and the system is five capabilities stacked in strict dependency order. Each one only works if the one before it does — which is why the order also tells you what to build first and what to prove in the pilot.

1
LOCATEWhere is the asset, now and over time. Free from the moment any device reports — needs no CAN, no adapter, no program number.
2
RECONSTRUCTTurn a stream of points into trips, idle, and time-on-site. Application logic over the position feed.
3
DETECTGeofences, unauthorised movement, over-speed, harsh driving. Device- and rules-driven; still no ECU needed.
4
ATTRIBUTEWhich client, which contract, which period does this record belong to. Requires dated assignment windows — the tenancy problem.
5
EVIDENCEEngine hours from the ECU, stored tamper-evidently, sealed into a utilisation certificate that survives a dispute. Everything above exists to make this trustworthy.

The pipeline that delivers those five is not exotic, but each stage has one non-obvious rule that separates a system that settles a dispute from one that merely draws a map:

StageWhat it doesThe rule that matters
TerminateHold the TCP socket, complete the IMEI handshake, validate CRC-16/IBM, parse Codec 8/8E, return the 4-byte acknowledgementUse AVL acknowledgement mode and acknowledge only after the record is durably stored. The device deletes its only copy on ACK — acknowledge early and a crash loses billing data silently
NormaliseDecode into one agreed telemetry record shapeTag every value with its source — ecu vs estimated — and never merge them. A "not measured" is never written as zero
AttributeResolve the record to a tenantTenancy is a dated assignment resolved at the record's own timestamp, not a column on the asset. Machines change hands mid-hire; a tenant ID rewrites history
StoreHot (last state), warm (time-series), cold (immutable evidence)Idempotent on record identity, not delivery — devices replay buffers out of order after an outage. Late writes must be free
SurfaceScreens, geofence rules, WhatsApp alerts, client tracking linksTreat WhatsApp as a first-class channel, and shared tracking links as expiring credentials
SealUtilisation periods, gap accounting, signed manifest chainDisclose gaps, never infer idle across them. A sealed period points at an immutable object version; corrections are new rows

The concrete build — and it rides your existing stack

Your three MVPs already run on Vanilla HTML/CSS/JS + Supabase + Vercel. The GPS backend does not need to break that pattern, and shouldn't. The lowest-risk implementation is almost embarrassingly small:

A
TERMINATORAdopt Traccar (open-source) on a single small VM. It speaks Codec 8E natively, keeps a device registry, and exposes a REST API. Days to first data, not weeks.
B
STOREOne Postgres — your existing Supabase, or self-hosted — with PostGIS for geofencing and time-partitioning (or TimescaleDB if self-hosted) for the telemetry table. Cold evidence in object storage from day one, separate and immutable.
C
SURFACEWire the seven Fleet screens you already have to live data through a thin API. This is integration, not design work.
D
CONTRACTBetween A and B sits your telemetry record shape. Nothing above it knows which terminator produced the data — which is what makes swapping Traccar for a custom gateway later a contained change.

That is a two-component ingestion path (Traccar + Postgres) feeding screens that already exist. It is the honest shape of the pilot — and it is a very long way from the multi-service cloud architecture that appears elsewhere in your own documents, which is the subject of the next section.

04Two architectures in your repo — pick one

This is the most important thing an outside reader notices: your documents describe two different systems, and nobody has said so out loud. Resolving this is worth more than any other single decision here, because it changes the cost, the team and the timeline all at once.

Architecture in the BRD's "In Scope"

HeavyAWS IoT Core, an ECS protocol bridge, Lambda → TimescaleDB, ASP.NET Core, Vue, MQTT internally. A managed-cloud, multi-service design — the instinct of an AWS-partner scoping call.

Architecture in your engineering reference

LeanAdopt Traccar, one Postgres + TimescaleDB + PostGIS, pooled tenancy with row-level security, reversibility via an owned telemetry contract. The design of someone who has costed this at pilot scale.

These are not two flavours of the same plan. They imply different teams, different bills and different risk. The lean one is correct for where you are, and the reason is a hard technical fact, not a preference:

AWS IoT Core cannot terminate these device connections. The FMC130 sends Codec 8/8E binary frames over raw TCP or UDP — there is no MQTT publish path and no HTTPS on the device. IoT Core expects MQTT/HTTPS. So the moment you choose IoT Core you must also build a custom TCP bridge in front of it — and then you are paying for and operating a managed broker that your fleet can't speak to directly. You've taken on the hard part (the bridge) and added a component you underuse.

The three honest paths

PathWhat it isComponentsVerdict
A · AdoptRun Traccar (or a commercial terminator); it parses Codec 8E and hands you the stream2Pilot Days to data. Strongest starting point
B · BridgeCustom TCP bridge in front of AWS IoT Core4+Avoid Worst of both — build the bridge and pay for a broker you can't use fully
C · BuildPurpose-built terminator (e.g. Go) you own end to end4Later Strongest acknowledgement control. Justified once engine hours bill an outside party

The migration trigger from A to C is not a device count — it is the first utilisation record issued from this data to someone outside your team. Until then, adopting a tested terminator is not a compromise; it is the right engineering call. And Teltonika's Duplicate server mode lets you run the old and new terminators in parallel, losslessly, whenever you switch — so the decision is fully reversible if you keep the telemetry contract yours.

What this means for the AWS / SUDO conversation

Your latest position with SUDO is already the healthy one — you build the application layer, they advise on the AWS layer. Good. But make sure the AWS advice is a Well-Architected review of a Traccar-on-a-VM + one Postgres design, not a Well-Architected review of an IoT-Core-bridge design. The same partner, pointed at the wrong architecture, will happily help you build the expensive one well. The architecture question comes before the cloud-review question.

05What competitors and the market run on

"What are competitors using" has two useful answers, because you compete on two fronts: against telematics platforms you could buy instead of build, and against the machine makers' own OEM telematics. Both matter, and the second is under-appreciated in your docs.

The platform market — the ceiling on what building is worth

Terminating Codec 8E, decoding CAN, running a device registry and storing telemetry is not novel work. Several companies sell exactly this, and Teltonika is among the most widely supported hardware in that market. The honest framing your Supplier Shortlist already reaches is worth repeating: the alternative to a five-month build is not a longer build — it is a subscription and an integration.

VendorWhereWhat it isWhy it matters to you

The screening question that cuts through all of them, in one call: "Do you support the FMC130 with the ALL-CAN300 adapter, and can you show me engine hours decoded from my machine models?" A live demo on your equipment is worth more than any proposal. If they can't, they are not in this market — whatever their website says.

The OEM telematics path — the option your docs barely mention

Every major equipment maker already ships telematics: Cat Product Link, Komatsu KOMTRAX, Volvo CareTrack, John Deere JDLink, Hitachi ConSite. These report OEM-authoritative data — including engine hours — from the factory, without anyone touching the CAN bus. And there is a standard, ISO 15143-3 (the AEMP telematics standard, "AEMP 2.0"), that exposes a common mixed-fleet API across brands.

This is strategically important for one reason: the machines that can't get a Teltonika program number are often exactly the ones that already have OEM telematics. For a modern Cat excavator on long-term hire, pulling ISO 15143-3 engine hours from Product Link may be a faster, cleaner route to evidence-grade data than fitting an FMC130 + ALL-CAN300 and hoping the make/model/year is on the supported list. A mature platform blends both: your own devices where you need control and coverage, OEM feeds where they exist.

The build-vs-buy verdict

The strongest position — and the one your own architecture already argues for without framing it this way — is a middle path: buy the ingestion, own the model. Let Traccar or flespi terminate the devices; keep the telemetry contract, the tenancy model and the evidence store in-house. That is the reversibility rule applied to procurement, and it means the answer to "build or buy?" is "buy the commodity, build the moat."

One caveat on local competition: I can't verify named UAE construction-telematics rivals from here, and I'd treat any such list with suspicion anyway. The highest-signal source on who actually deploys well in the Emirates is a single phone call to your device distributor — they know which local integrators deploy FMC130s and which installs come back broken. That is the competitive intel worth having.

~9 people (1 solutions architect, ~5 developers, 1 DevOps, 2 QA) over 5 months. First milestone: a display / dashboard POC. Roughly 45 person-months of software.

What the work actually is

One telemetry contract, one schema, one tenancy model, one ingestion path, plus wiring screens that already exist. Roughly 9 person-months — two engineers and a part-time coordinator.

Credit where due: five months to a pilot is roughly the right duration, wanting an architect on it is sensible, and thinking about QA at all puts them ahead of many. This is not a bad team; it is a team that has been handed no written scope and has answered with a template.

The single question that settles the team-size debate without a fight

"Can you break the five months into person-months by area — ingestion, data model, screens, reporting, infrastructure, testing — and name the five developers' workstreams and the interfaces between them?" A team that has done this answers immediately and may revise the number themselves. A team that can't produced the estimate from a staffing template — and now you both know it, without you having to say so.

The better shape — buy the first six weeks, not the five months

Keep the same duration and team if you like, and change one thing: what month one proves. Swap the display POC for a thin vertical slice — one real device, through a listener, into a store, with engine hours on one screen. It answers the design-invalidating questions in week five instead of week thirteen, gives an honest demo, and produces a re-estimate grounded in real work. Commercially: commit to a fixed-price, fixed-deliverable six weeks, then re-scope. If a team can't deliver that slice in six weeks with three people, the five-month plan was never going to hold anyway.

Two teams means the risk is at the seam

You own hardware; they own software. The most likely cause of a slip is a handoff neither plan mentions. Date these four now: (1) the endpoint + TLS details they give you before any device ships; (2) two test units + live SIMs you give them; (3) the list of which machines can actually produce engine hours; (4) a working listener they operate before installs start — because otherwise nobody can verify a fit worked, and a device reporting position but no engine data looks perfectly healthy.

The reporting-interval decision swings your data cost 3–6×

Still open (D2). At 10s a device produces ~3,500 records/day; at 30s ~1,300; at 60s (the team's working assumption) ~560. Since your assets move slowly on sites and defined routes, 30–60s almost certainly captures everything operationally useful — and cuts storage and bandwidth several-fold. Even at a few hundred devices that is a few hundred million rows a year — comfortably within one tuned Postgres, which is why the database, not the socket server, is the thing to watch as you scale. Decide the interval before anyone sizes storage.

Two commercial figures to pressure-test

Pricing. Your docs quote AED 80–150/device/month, with tiers at 60/80/100. The expert review flags that the entry tier at AED 60 sits above the observed UAE market band of ~AED 30–50 for basic tracking — a real adoption risk for the "just see it" tier. Hardware-plus-engine-hours justifies a premium; basic location may not.

Break-even. The internal analysis lands around 351 devices to break even, with a recommended raise of AED 110–135k to fund the pilot and early scale. That is the number the business case should be built on, not the MRR-at-1,000-devices headline.

Hire, or contract a specialist?

For a project this size, one experienced telematics engineer is worth more than five generalists — and easier to find than the market suggests, because the people who've done this are visible. Look where the evidence is, not where the marketing is:

  • Open-source Codec 8E parser authors and Traccar contributors — they've demonstrably debugged real device traffic. Many are in Eastern Europe and Latin America rather than India, and several take contract work.
  • The Wialon partner map and Teltonika's software-providers list — everyone on them has integrated real devices to a real platform.
  • Your device distributor — the most under-used source of who deploys well locally.
  • The AIS-140 filter for Indian candidates — "Have you built an AIS-140-compliant backend? Walk me through the packet structure." India's mandatory vehicle-tracking standard requires real protocol work; a firm that's done it answers instantly, a firm that hasn't pivots to describing its dashboard.

The six-question technical screen — anyone who can't answer these hasn't done this work

  • Walk me through a Codec 8E session from TCP connect to the device clearing its buffer.
  • When do you send the acknowledgement? (The most revealing question — a real answer engages with acknowledging only after durable storage.)
  • A device reconnects after four hours offline and replays its buffer — what breaks?
  • How do you get engine hours off a machine that isn't a truck? (CAN adapter, J1939, and program-number dependency.)
  • How do you test before hardware arrives? (A traffic generator — else the schedule has a hole.)
  • What does a completed installation mean? (Data verified on the server, including engine hours.)

Red flags in any proposal

No hardware, procurement or installation in the plan · team size quoted before scope is agreed · a first milestone that is a UI · "we'll need to recruit for this" · vagueness about who owns the data model and code · no questions back (a supplier who's done this asks about your machine makes, reporting interval, fleet size and where data must live).

The cheapest way to choose well

Before any build, pay one specialist for two weeks to stand up an ingestion path against two real devices on a bench and report what the hardware actually does. It costs a fraction of a month of a nine-person team, answers the open protocol questions directly, and tells you more about whether someone can do this work than any interview. Run it with two candidates in parallel if the choice is close. Then contract discovery → pilot → scale, with the option to change supplier at each boundary — and keep the telemetry contract, schema and evidence store in-house whoever builds the ingestion.

11The next fourteen days

None of this needs the team hired, the supplier chosen, or the architecture finally settled. It is the set of moves that either unblock the critical path or cost nothing to start — do them in this order.

1Send the CAN program-number enquiry to Teltonika — this is the one that can't wait. List your real fleet by make, model and year and ask which have a supported ALL-CAN300 program and what each exposes (D1). Until this returns you cannot know which machines can bill on engine hours, and nothing can be ordered. It gates the whole field track.
2Order two test units with live SIMs — one FMC130 + ALL-CAN300 (heavy) and one FMC920 + LV-CAN200 (light) — so a bench exists the moment an engineer starts. Confirm the firmware shipping is 03.27.02 or later (D9); older units need a firmware pass on the critical path.
3Get device + adapter quotes at 10-unit and 100-unit volumes from the UAE distributor — the one price your documents don't contain — and ask the distributor who deploys Teltonika well locally.
4Reconcile the SIM cost with du and e& directly (the AED 10 vs 25–35/month conflict) and ask what a private APN into your network would take (D4).
5Decide the reporting interval (D2) — 30–60s almost certainly suffices for slow-moving site assets and cuts data cost several-fold. This unblocks every storage and bandwidth estimate.
6Pin down the hosting and residency direction (D3) and, with it, confirm exactly what SUDO's engagement covers — the technical pack now has them advising the AWS layer only, with you building the app layer. Make sure both sides read it the same way.
7Start the two-week bench discovery with a shortlisted specialist (section 10) — it can run in parallel with the hardware arriving and is the highest-signal, lowest-cost way to choose who builds the ingestion.
8Write the telemetry contract and traffic generator now — neither needs hardware. A generator emitting valid Codec 8E frames lets the software track begin against a bench of simulated devices while the real ones are still in a box.

Items 1–4 belong to the field track and one of them (the program numbers) sets your earliest possible pilot date. Items 5–8 are decisions and desk work you can complete regardless of hardware. Doing 1 late is the most expensive mistake available on this project; doing 8 early is the cheapest insurance.
